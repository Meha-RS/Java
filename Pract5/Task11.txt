Выбор коллекций по характеру нагрузки

1. Каталог по идентификатору — get/put O(1) в среднем
   - Интерфейс: Map<String, Course>
   - Реализация: HashMap
   - Обоснование: прямое обращение по ключу без порядка. Дополнительные расходы памяти на массив корзин, порядок обхода не определён.

2. Отсортированная таблица результатов — вставка и поиск O(log n)
   - Интерфейс: NavigableMap<Integer, List<Course>>
   - Реализация: TreeMap
   - Обоснование: требуется упорядоченность по баллам. Красно-чёрное дерево поддерживает сортировку, однако увеличивает расход памяти на узлы и уступает хеш-таблице в скорости точечного доступа.

3. Очередь ожидания — offer/poll O(1)
   - Интерфейс: Queue<Course>
   - Реализация: ArrayDeque
   - Обоснование: дисциплина FIFO без произвольного доступа. Кольцевой массив компактен по памяти и эффективен с обоих концов.

4. Уникальные теги с сохранением порядка — add/contains/remove O(1) в среднем
   - Интерфейс: Set<String>
   - Реализация: LinkedHashSet
   - Обоснование: необходимы уникальность и порядок первого появления. Двунаправленные связи между элементами сохраняют порядок ценой умеренного увеличения расхода памяти.

5. Диапазонный поиск — поиск границ O(log n), обход диапазона O(k)
   - Интерфейс: NavigableMap<String, Course>
   - Реализация: TreeMap
   - Обоснование: операции subMap и headMap/tailMap возможны лишь в отсортированной структуре. Хеш-таблица для интервальных запросов непригодна.

6. Частый доступ по индексу — get(i)/set(i) O(1), вставка в середину O(n)
   - Интерфейс: List<Course>
   - Реализация: ArrayList
   - Обоснование: непрерывный массив обеспечивает наиболее компактное хранение и мгновенный доступ по позиции. Цена — сдвиг элементов при вставке в середину.
